# Инфраструктура: целевая схема и переезд

Прод сейчас живёт на личном сервере разработчика. Его нужно перенести на сервер института и заодно перестроить так, чтобы проект мог расти: два стенда, выкладка только через CI, никакого состояния внутри контейнера.

Схема повторяет стандарт института (вики «CI/CD Instructions»: стенды, GitHub Actions, Docker Hub, Portainer). Где вики расходится с живыми проектами, выбор указан явно.

## Стенды и ветки

| Стенд | Ветка | Домен | База |
|---|---|---|---|
| dev (превью) | `dev` | `dev.psyo.ru` | своя, обезличенная копия прода |
| prod | `main` | `psyo.ru` | боевая |

- Работа идёт в фича-ветках, PR вливается в `dev`. После пуша в `dev` превью обновляется само.
- На прод изменения попадают только через PR `dev` → `main`. Прямых пушей в `main` нет: ветка защищена, нужен зелёный CI.
- Рабочее дерево на сервер не копируется, `docker build` на сервере не запускается. Всё собирается в CI.

## Пайплайн (GitHub Actions)

1. **PR в `dev` или `main`:** `npm ci` → `npm run lint` → `npm test` → `npm run build`. Красный CI блокирует merge.
2. **Push в `dev`:** собирается образ, тег — короткий SHA. Образ уходит в Docker Hub института, затем дёргается webhook Portainer стека `dev-mipsy`. После выкладки проверяется `/api/health`.
3. **Push в `main`:** то же самое для стека `prod-mipsy`. Перед выкладкой снимается дамп прод-базы, потому что миграции назад не откатываются.
4. **Откат:** в Portainer прописывается предыдущий SHA. Старые образы остаются в registry.

Секреты CI (доступ к Docker Hub, webhook-и) лежат в GitHub Secrets. Секреты приложения хранятся в `.env` на сервере, у каждого стенда свой файл. В образ они не вшиваются.

## Что поменять в приложении

Чтобы контейнер можно было пересоздать, перенести или запустить в нескольких копиях, состояние выносится из него наружу.

- **SQLite → Postgres.** Postgres — стандарт института, и он даёт отдельные базы на каждый стенд, нормальные дампы и одновременную запись. Нужно перевести схему drizzle на `pg-core`, переписать миграции и `scripts/migrate.mjs` и запускать тесты на Postgres.
- **Файлы → S3.** Шов уже есть, это `src/lib/storage.ts`. Бакет должен быть в РФ, отдельный на каждый стенд.
- **Планировщик напоминаний** сейчас крутится внутри процесса Next (`src/lib/reminder-scheduler.ts`). Если запустить две копии приложения, напоминания уйдут дважды. Его нужно вынести в отдельный контейнер-воркер или в cron по HTTP.
- **Превью не должно видеть живых клиентов.** Данные о психологическом состоянии относятся к особой категории персональных данных (152-ФЗ). Базу dev-стенда заполняет скрипт: он копирует прод и обезличивает имена, почты, телефоны и тексты анкет. Отдавать превью прод-базу даже в режиме read-only нельзя.

## Требования к серверу

Один сервер под оба стенда, как у остальных проектов института.

| | Минимум | Рекомендуем (с запасом на рост) |
|---|---|---|
| CPU | 2 vCPU | 4 vCPU |
| RAM | 4 ГБ | 8 ГБ |
| Диск | 40 ГБ SSD | 80 ГБ NVMe |
| ОС | Ubuntu 24.04 LTS | |
| Расположение | РФ (152-ФЗ, локализация персональных данных) | |
| Сеть | белый IPv4, наружу открыты 22, 80, 443 | |

Откуда такие цифры: на сервере крутятся два контейнера Next (по 200–400 МБ), два Postgres (по 0,5–1 ГБ), nginx, Portainer и воркер. Сборка на сервере не идёт, поэтому запас по CPU нужен только под нагрузку. Когда прод упрётся в ресурсы, первым делом стоит отселить dev-стенд на отдельную машину.

## Что ещё нужно для переезда

От института:
- сервер по таблице выше и root-доступ для первичной настройки;
- доступ к Docker Hub института и Portainer, либо установка Portainer на новом сервере;
- S3-бакеты (prod, dev, бэкапы) в РФ: Yandex Object Storage, Selectel или reg.ru;
- почтовый ящик или SMTP-сервис на домене института для писем с кодами входа;
- владелец домена `psyo.ru`: доступ к DNS для A-записей `psyo.ru` и `dev.psyo.ru`;
- GitHub-организация института, куда переедет репозиторий;
- проверить, на кого оформлены магазин ЮKassa и SMS-провайдер, и при необходимости переоформить.

Порядок:
1. Перевести приложение на Postgres и S3, вынести планировщик. Всё это вливается через `dev`, проверяется на текущем сервере.
2. Поднять на новом сервере nginx, certbot, Portainer и стеки `dev-mipsy` и `prod-mipsy`, подключить CI.
3. Поднять dev-стенд на `dev.psyo.ru` и прогнать на нём весь путь клиента и психолога.
4. Перенос прода. Включить режим обслуживания, снять финальный бэкап SQLite, перелить данные в Postgres и файлы в S3, переключить DNS, выпустить сертификат.
5. Через несколько дней без инцидентов удалить mipsy со старого сервера: контейнер, данные, cron, конфиги nginx.
