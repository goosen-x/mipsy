# Отчёт по приложению · аудит 15.08.2026

Перенесено из служебной страницы `/admin/report` (удалена 17.08 по решению
пользователя — отчёту не место в продуктовой админке). Три независимые ревизии
кода — бизнес-логика, схема БД и чистота кода, тесты и охота за багами. Всего
~45 подтверждённых находок; всё критичное исправлено в тот же день (коммиты от
15.08, миграция 0015, тестов стало 67).

## Оценки по измерениям

- **Бизнес-логика — 4−.** Ядро (вход по коду, брони с защитой от гонок, правило 24 часов, модерация с грейдами) спроектировано аккуратно. Дыры жили на стыках состояний — переподбор, скрытие психолога, операторские действия; все закрыты каскадами и письмами.
- **Структура БД — 3+ → 4.** Схема осмысленная, но инварианты держались на комментариях: не было ни одного CHECK и почти ни одного индекса. Миграция 0015 добавила 3 уникальных ограничения и 7 индексов под реальные запросы. Осталось: enum-статусы всё ещё строками без CHECK, мёртвые колонки не удалены (осознанно).
- **Покрытие тестами — 4.** Чистые модули (booking, matching, rules, auth-core, ics, datetime, grades) покрыты добротно, включая миграции против копии боевой базы. После аудита добавлены тесты на гонки и каскады (67 всего). Не тестируются server actions и БД-часть auth — архитектурно заперты server-only-импортами.
- **Чистота кода — 4.** Все 40+ server actions проверяют сессию, слоение auth-core/домен/экшены выдержано, мёртвого кода нет. Налёт MVP: дубли мелких выборок, три формата дат (шов теперь именован: formatDbTime), разнобой типов ответов экшенов.

## Исправлено (21)

- Переподбор не гасил старые предложения: клиент видел «подбираем нового» и календарь отвергнутого психолога одновременно, оператор упирался в лимит трёх вариантов и не мог снять выбранного
- Скрытие или отклонение психолога бросало его клиентов: теперь каскад — предложения гаснут, будущие брони освобождаются, заявки уходят в переподбор, клиенты получают письмо
- Запись и снятие записи оператором не слали никому писем — клиент оставался без ссылки на встречу и приглашения в календарь
- Авторизация админки жила только в layout — Next не перерендеривает его при мягкой навигации; теперь requireAdmin() на каждой из 12 страниц
- Гонка двойного переноса: две параллельные операции давали клиенту две брони и дублировали отметку оплаты; переходы слота стали атомарными (условные UPDATE)
- Гонки: двойной отзыв об одной встрече, перезапись исхода done→no_show, дубли окон при параллельном открытии расписания — закрыты уникальными индексами и условными UPDATE
- Прошедшую встречу можно было отменить прямым вызовом экшена и увернуться от «не пришёл» — теперь сервер отказывает с честным текстом
- Кризисная анкета уходила в самозапись до звонка оператора — автоподбор для кризисных отключён, заявка ждёт приоритетного звонка
- Расписание принимало несуществующие даты («2026-13-01» роняло экшен, «31 февраля» молча становилось 3 марта) и отрицательную длительность
- Скрытый психолог был доступен для брони прямым вызовом экшена и предлагался оператором в подборе
- Клиент, скрытый с будущими бронями, гарантировал психологу неявку — теперь брони снимаются с письмом психологу
- Неявка ставилась молча — теперь клиент получает письмо с выходом в поддержку («если это ошибка — разберёмся»)
- Оператору нечем было отметить оплату после сессии (переключатель был только у будущих) — добавлен психологу и у прошедших встреч
- У психолога не было канала поддержки — в кабинете появилась форма обращений (спорные записи, неявки)
- Перенос брони, сделанной у другого специалиста, вёл в тупик «время недоступно» — календарь переноса теперь берёт окна психолога конкретной брони
- Рейтинг считался двумя формулами: каталог — по всем отзывам, профиль — по последним 10; выровнено
- Контакты уведомлений добираются из аккаунта (бронь из каталога создавала заявку без телефона — SMS-канал умирал навсегда)
- Аналитика мешала UTC и МСК: заявки после 21:00 UTC падали «во вчера»; все времена в админке переведены в МСК с пометкой
- Анонимный отчёт об ошибках без лимита позволял заливать журнал — введён потолок 20 записей в минуту
- Валидация входа: возраст 16–100, оценка отзыва — целое 1–5, лимиты длин текстов, почта до 254 символов, статусы заявок/тикетов — по белому списку
- Тексты, противоречащие поведению: FAQ про «цену указывает специалист», «выберите другого ниже» без секции ниже, устаревшие docs/spec о бесплатной первой встрече

## Отложено осознанно (9)

Дублируются в `backlog.md` («Отложено по аудиту 15.08») — актуальный статус там.

- Отзыв старого .ics-события при переносе/отмене (METHOD:CANCEL) — нужен рефактор рассылки приглашений
- SESSION_SECRET с фолбэком на константу — на проде секрет задан; менять поведение при деплое осторожно
- Кука сессии без срока внутри подписи, отзыва сессий нет — приемлемо для MVP
- Статусы-enum без CHECK; «на доработку»/«черновик» у психолога; «форс-мажор» у встречи — миграции-перестройки и продуктовые решения
- Мёртвые колонки (format, price, intro_call_enabled, cabinet_token, client_token) — перестройка таблиц SQLite ради нуля пользы
- Дубли мелких выборок и 600-строчный admin/controls.tsx — сводить по мере правок
- БД-часть auth не тестируется — нужен рефактор «база параметром» по образцу booking.ts
- Нет транзакции вокруг «заявка + бронь + matches» — компенсация есть, атомарности нет
- notifications.recipient_phone NOT NULL с сентинелом «» — перестройка таблицы

## Главный архитектурный вывод

Почти все серьёзные находки жили на стыках состояний: одна таблица менялась, а
зависимые (предложения, брони, оплата, письма) отставали. Рецепт, который
теперь применён и которого стоит держаться дальше: каждый переход состояния —
переподбор, скрытие, отклонение — проходит через один доменный модуль
(booking.ts, matching.ts), который обязан ответить на три вопроса: что с
предложениями, что с бронями, кто получает письмо. Экшены остаются тонкими
переходниками, а инварианты — в схеме БД, а не в комментариях.
